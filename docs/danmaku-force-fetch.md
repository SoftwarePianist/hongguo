# 短剧弹幕强制拉取：实验结论与后续开发方案

> 状态：弹幕实现代码已回滚，本文档保留。下次开发应先恢复诊断，再根据证据决定是否恢复强制补拉。
>
> 最近验证环境：红果短剧海外版 `7.3.5.32`。混淆类名、接口参数和行为均需在目标版本上重新确认。

## 1. 需求与完成标准

目标不是简单地“多请求一次”，而是可靠地区分以下情况：

1. 当前剧集没有发起弹幕请求。
2. 请求失败或超时。
3. 请求成功，但服务器返回 0 条弹幕。
4. 服务器返回了弹幕，但没有交给渲染层。
5. 渲染层收到弹幕，但界面没有显示。

只有确认属于第 1 类，并且主动补拉能增加有效弹幕时，才保留“强制拉取”功能。

验收标准：

- 每次进入或切换剧集后，都能在诊断中找到一条对应样本。
- 样本至少包含剧集标识、原生请求、补拉请求、响应状态、返回数量、渲染数量和最终结论。
- 没有弹幕时，诊断必须明确显示“服务器返回 0 条”或“未发起请求”，不能只显示“0 条”。
- 强制补拉不得重复请求同一剧集、阻塞主线程或影响原生播放。

## 2. 已完成的实机验证

本轮曾实现并安装过弹幕诊断、最近播放样本和强制补拉，然后使用同一剧集反复对照：

- 关闭强制补拉时记录弹幕数量。
- 重新进入相同剧集，开启强制补拉后再次记录。
- 开启与关闭时获得的弹幕数量一致，强制补拉没有带来增量。

当前结论：当红果已经正常发起原生请求时，重复请求相同接口只会拿到相同的数据。现有证据不支持长期保留强制补拉代码，因此实现已回滚。

这个结论不等于“以后不需要开发”。如果后续诊断捕获到“某集没有原生请求，而手动补拉后返回大于 0 条”，再恢复补拉才有价值。

## 3. 评论数与弹幕数不是同一指标

剧集页显示的“评论数”不能作为弹幕数量使用。

- 剧集详情数据中的 `comment_count` 是评论相关的汇总字段。
- 弹幕接口使用 `comment_type = 20`，并按播放时间窗口返回带 `offset_time` 的数据。
- 因此“第 1 集有 200 多条评论”与“弹幕接口返回 0 条”可以同时成立。

诊断界面和日志必须分别命名为“评论元数据数”和“弹幕响应条数”，禁止合并统计。

## 4. 红果弹幕接口证据

参考项目：[huangxd-/danmu_api](https://github.com/huangxd-/danmu_api)，核对提交 `28673ac764485b0f37966779bc3b14e2b97d31aa` 中的 [`danmu_api/sources/hongguo.js`](https://github.com/huangxd-/danmu_api/blob/28673ac764485b0f37966779bc3b14e2b97d31aa/danmu_api/sources/hongguo.js)。

该实现展示了以下红果链路：

### 4.1 获取剧集信息

```text
POST /novel/player/multi_video_detail/v1/
```

主要输入是 `series_id`。响应中的 `video_list` 提供：

- `vid`：弹幕接口路径和 `group_id` 使用的视频标识。
- `vid_index`：集数。
- `duration`：分页边界所需的视频时长。
- `comment_count`：评论元数据，不等于弹幕返回条数。

### 4.2 获取弹幕

```text
POST /novel/commentapi/comment/list/{vid}/v1/
```

关键请求字段：

```json
{
  "comment_source": 601,
  "server_channel": 1000,
  "group_id": "当前剧集 vid",
  "group_type": 30,
  "comment_type": 20,
  "sort": 1,
  "business_param": {
    "book_id": "series_id",
    "start_offset_time": 0,
    "playlet_item_duration": "剧集时长，毫秒",
    "need_danmaku_guide_type": [1, 3, 4, 2]
  },
  "count": 90,
  "cursor": ""
}
```

请求还需要红果运行时生成的签名和会话信息。不要在模块中固化第三方仓库里的设备 ID、Cookie、Token 或签名密钥；优先复用目标 App 自己的请求对象和网络链路。

### 4.3 分页与响应解析

- 每次按约 30 秒播放区间请求。
- 下一页时间优先读取 `data.extra.next_query_danmaku_list_time`。
- 游标读取 `data.common_list_info.cursor`。
- 是否继续读取 `data.common_list_info.has_more`，同时受剧集时长约束。
- 弹幕列表位于 `data.data_list`。
- 文本位于 `comment.common.content.text`。
- 出现时间位于 `comment.expand.offset_time`，单位为毫秒。
- 可使用 `comment.comment_id` 去重，缺少 ID 时用“时间 + 文本”作为退化键。

这些字段用于离线理解协议；模块内仍应以运行时原生对象为准，避免版本更新后 JSON 字段或签名规则失效。

## 5. 推荐实现顺序

### 阶段一：只恢复诊断

复用当前项目的 `LogUtil` 和设置面板，不新增依赖。监听原生弹幕请求与响应，建立每集状态：

```text
进入剧集
  -> 等待原生请求
  -> 记录响应状态和条数
  -> 记录渲染层接收条数
  -> 生成最终诊断
```

建议状态值：

```text
WAITING_NATIVE
NATIVE_NOT_SEEN
REQUEST_FAILED
SERVER_EMPTY
SERVER_HAS_DATA
RENDER_NOT_SEEN
RENDERED
```

不要仅依赖实时日志。诊断页必须能够查看最近播放样本。

### 阶段二：保存最近样本

使用现有 `SharedPreferences` 保存定长 JSON 列表即可，建议最多 20 条，不引入数据库。每条样本包含：

```text
sampleId
seriesId / vid / episodeIndex
enteredAt / finalizedAt
forceEnabled
nativeRequestCount
forcedRequestCount
httpStatus / error
serverItemCount
renderItemCount
diagnosis
```

同一次进入剧集生成一个 `sampleId`。切集、退出播放页或超过诊断窗口时完成样本，避免多个剧集的数据串在一起。

### 阶段三：有证据时才恢复补拉

触发条件必须同时满足：

1. 总开关和强制补拉开关已开启。
2. 已获得当前剧集的 `seriesId`、`vid` 和时长。
3. 进入剧集后的观察窗口内没有看到原生弹幕请求。
4. 当前剧集尚未补拉过。
5. App 仍在播放同一剧集。

补拉应调用红果原生请求方法或重放原生请求对象，让 App 自己提供签名、Cookie、设备参数和响应模型。不要自己维护完整的接口签名算法。

补拉完成后仍需走原生解析和渲染链。如果只拿到了网络响应但没有送到渲染层，功能仍未完成。

## 6. 诊断判定规则

| 观测结果 | 最终结论 | 后续动作 |
| --- | --- | --- |
| 观察窗口内没有原生请求 | App 未触发弹幕拉取 | 可以尝试一次补拉 |
| 请求异常、超时或非成功状态 | 弹幕请求失败 | 记录错误，不无限重试 |
| 请求成功且响应条数为 0 | 服务器本集无弹幕 | 不补拉 |
| 响应条数大于 0，未观察到渲染调用 | 数据未进入渲染层 | 排查解析、回调和生命周期 |
| 渲染层收到大于 0 条，屏幕仍不可见 | 显示链路异常 | 排查弹幕开关、View 可见性和过滤规则 |
| 原生与补拉返回数量一致 | 补拉没有收益 | 保留诊断，关闭补拉 |
| 原生未请求，补拉返回大于 0 条 | 补拉有效 | 才考虑正式保留功能 |

最终诊断必须来自本次剧集样本的完整链路，不能把“没有捕获到结果”误判为“服务器返回 0 条”。

## 7. 与“自动最高画质”的对应关系

自动最高画质的工作方式是：在 `setVideoModel` 或原生控制器链路中获得当前视频模型和最高分辨率，然后调用 App/播放器已有的应用方法。

弹幕功能应采用相同原则：

- 播放模型或 holder 绑定用于确定“当前是哪一集”。
- 原生弹幕请求 Hook 用于确认 App 是否拉取以及获得可复用的调用上下文。
- 只有原生请求缺失时才主动调用 App 自己的拉取方法。
- 原生响应和渲染 Hook 用于证明弹幕最终到了哪里。

两者的差别是：画质只需应用一个确定值，而弹幕包含网络、分页、解析和渲染四段链路，不能把“发出请求”等同于“显示成功”。

## 8. 预计代码落点

恢复开发时优先控制在现有文件内：

- `Hooks.kt`
  - 读取弹幕诊断/补拉开关。
  - 监听剧集切换、原生请求、响应和渲染。
  - 维护当前样本并保存最近 20 条。
  - 在满足条件时执行一次补拉。
- `TargetNames.kt`
  - 仅在确认必须依赖混淆类名时增加版本映射。
- `LogUtil.kt`
  - 只有现有计数和日志能力不足时再修改。

不建议新增独立网络客户端、数据库、后台 Service 或复杂仓库层。

## 9. 风险与保护措施

- 红果请求包含签名和设备/会话字段，手工拼装容易失效或触发风控。
- 分页请求必须去重、节流，并设置单集最大请求次数。
- 切集后延迟返回的旧响应不得计入新剧集。
- Hook 失败只能让增强功能失效，不能阻断原生请求或播放。
- 日志和历史样本不得保存 Cookie、Token、完整签名参数或可识别设备的信息。
- App 升级后，应先验证接口路径、请求模型、响应模型和渲染入口，再更新 `TargetNames`。

## 10. 最小验证矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| 正常有弹幕的剧集 | 原生请求、服务器条数和渲染条数均大于 0 |
| 服务端空数据的剧集 | 请求成功，明确记录 `SERVER_EMPTY` |
| 人为阻断请求 | 明确记录请求失败，不能显示为服务器空数据 |
| 原生请求未触发 | 明确记录 `NATIVE_NOT_SEEN` |
| 同一集关闭/开启补拉 | 分别保存两个独立样本，可直接比较数量 |
| 返回有数据但不显示 | 能区分解析/渲染未调用与 View 不可见 |
| 快速连续切集 | 每条响应只归属正确的 `vid` |

## 11. 下次继续开发的启动清单

1. 确认目标 App 包名、版本名和版本号。
2. 重新定位原生弹幕请求、响应模型和渲染入口。
3. 先恢复诊断与最近样本，不恢复补拉。
4. 连续采集多集，至少包含有弹幕和无弹幕样本。
5. 找到真实的 `NATIVE_NOT_SEEN` 样本后，再增加一次性补拉。
6. 使用同一集做开关对照；只有补拉产生增量才保留功能。
